# OpenCode 订阅接入（第四家本机订阅大脑）

> 2026-10-14：新增 `cli-opencode` 本机订阅大脑。本文记录实测依据、隔离方案、修改清单与验证结果。
> 使用说明见 [model-access.md](model-access.md)「OpenCode 订阅」一节；架构与边界见 [orchestrator README](../orchestrator/README.md)「大脑」。

## 核心结论

opencode CLI 具备接入本工作台所需的全部基础能力，作为第四家本机订阅接入（`cli-opencode` → `opencode run --format json`）。
与另外三家同一套纪律：用户自己的登录、产品只经受控工具做事、事件流白名单越界即杀进程树、不读不存任何登录凭据。

与三家的差异（界面与文档如实声明）：

- OpenCode 是**任意模型网关**：登录 = 用户在 `opencode auth login` 配置的凭据（订阅 OAuth 或 API key 都存在
  OpenCode 自己的数据目录）。产品不传模型名、不区分登录方式，探针只认**存储凭据（stored credential）非空**；
  外壳环境变量连接（environment）不算登录。
- **会话会落盘**：OpenCode 目前没有「禁止会话落盘」的开关，每次会话（含研究阶段）写进用户自己的
  `~/.local/share/opencode/`（`XDG_DATA_HOME` 可重定向）。这是它与 Claude / Codex / CodeBuddy 的主要差异。
- 无 `--system-prompt` 与结构化输出参数：系统提示词与 JSON Schema 经内联 agent 承载，产物由产品 validator 把关
  （与模型 API 未实测模板同一条 `structuredOutput: "prompt"` 语义）。

## 实测依据（Windows，opencode 1.19.0）

| 能力 | 实测结论 |
|---|---|
| `run --format json` | 逐行 JSONL 事件：`step_start` / `text` / `tool_use` / `step_finish` / `error`；成功收尾 = `step_finish` 且 `reason:"stop"` |
| 提示词 | argv 只带位置参数占位，stdin 与 message 合并 → **正文走 stdin，argv 不带用户内容** |
| 登录探测 | `opencode auth ls`（1.19.0 无 `--format json`）；固定输出两段：`Credentials <auth.json 路径>` 段 + 计数行 `<N> credentials`（带 `—` 装饰前缀）、`Environment` 段 + `<N> environment variable(s)`。仅存储凭据计入登录；环境变量连接不算。默认数据目录 `~/.local/share/opencode/auth.json`（`XDG_DATA_HOME` 可重定向，实测生效）。更高版本的「No authenticated integrations」整表文案同样兼容；读不懂一律按「检测未完成」失败，不误判 |
| Windows 包装器 | npm 对 `bin/opencode.exe` 也会生成 `opencode.ps1` 包装器，但内容是 `& "$basedir/node_modules/opencode-ai/bin/opencode.exe" $args`（直接调包内 exe，不是 node shim）。适配层的 shim 解析支持两种形态：node shim（`node$exe` → 由当前 Node 运行）与原生 exe shim（返回该 exe 直接运行）；目标唯一且文件存在才放行 |
| help 通道 | `opencode run --help` 输出到 **stderr**（stdout 为空）——能力闸按双流合并判定 |
| 权限隔离 | `OPENCODE_CONFIG_CONTENT` 环境变量整份内联注入（零配置文件）：`permission: {"*":"deny"}` 后内建工具（bash/edit/read/glob/grep/webfetch/task/question...）全部不可执行；MCP 工具按 **`<namespace(server)>_<tool>`** 的 permission 键精确 allow（`packages/core/src/tool/mcp.ts` 的 `name()`；server 与 tool 里的非 `[A-Za-z0-9_-]` 都替换成 `_`） |
| MCP | 配置段 `mcp.{name}.type:"local"` + `command:[...]`（cmd 数组）+ `environment` + `timeout:600000`；stdio 服务器响应必须带 `"jsonrpc":"2.0"` 字段，否则 SDK 解析帧失败、连接 30 秒超时（实测坑） |
| 系统/能力闸 | `--pure` 排除外挂插件；`--agent` 指定内联 primary agent（承载系统提示词与该 agent 私有 permission）；内联 agent 段的 prompt/permission 实测生效 |
| 非交互的 ask | `permission` 配置里未放行的 `ask` 请求由 CLI 自己 auto-reject 并提示模型改行 —— 产品不用 `--auto`（它会放行未显式 deny 的一切，危险） |
| 环境变量 | `OPENCODE_DISABLE_AUTOUPDATE=1`、`OPENCODE_DISABLE_LSP_DOWNLOAD=1`；外壳遗留的 `OPENCODE_CONFIG` / `OPENCODE_CONFIG_DIR` / `OPENCODE_PERMISSION` 不透传（内联注入说了算） |

最低版本定 `1.19.0`（实测版本）。permission 体系要求 v1.1.1+；旧版不点亮卡片。

## 隔离与安全边界

- **permission 双保险**：第一道门是内联 `permission: {"*":"deny"}` + 只 allow 产品 MCP 工具；真正的兜底是
  `OpenCodeEventStream` —— 事件流中出现白名单外的 `tool_use`（或未知事件类型）立即终止整棵进程树，
  白名单内工具调用按次数封顶（`max(32, maxTurns*8)`）。
- **探针最小化**：`probeOpenCode` 只返回版本与「是否配置过模型」两个布尔结论；`auth ls` 的原文（行里带打码凭据名）不进浏览器、日志或状态。
- **环境白名单**：沿用 `localSubscriptionEnv`；OpenCode 的登录在通用列表已有的 `XDG_DATA_HOME` 下，执行时
  产品的隔离配置由 `OPENCODE_CONFIG_CONTENT` 现做现传（研究子进程不需要也不可能继承到它）。
- **执行前复核**：每次 `runLocalAgent("opencode")` 前重探版本、`run --help` 能力参数与 stored 登录；任一不过关直接报错，不启动研究进程。
- 模型覆盖问题不存在：产品不传模型参数，OpenCode 用用户自己配置的默认模型。

## 已知限制与待办

1. 未做真实 OpenCode 订阅的**服务级六阶段冒烟**（需启动服务并消耗一次真实额度）；实施前应与其它三家一样进发布验收（见 release-checklist 第 5 条）。
2. 会话落盘无法关闭：文档已如实声明；若 OpenCode 未来提供禁用开关，可收进隔离配置。
3. `opencode auth ls` 的输出格式随版本演进（1.19.0 的计数行、更高版本的「No authenticated integrations」整表）：
   解析按「读不懂一律失败」的口径写死，升级时按 1.19.0 与目标版本实测回归探针（现有 FAKE 探针矩阵可扩展）。
4. OpenCode 的模型凭据可能是各家 API key：与产品「免 key 口径」并行的只有「用你在 OpenCode 里已配置好的模型」的
   如实表述，不能说成某家的订阅。
5. 本机进入方式：装在别的位置可用环境变量 `OPENCODE_BIN` 指定（页面不能改）。

## 实机接入后修复（2026-10-14 同日）

用户在设置页第一次点「重新检测」暴露三个探针层问题，已同日修复：

1. **npm 包装器形态**：`findExecutable` 选中的是 `opencode.ps1`（npm 对 exe bin 也生成包装器），其内容不调用
   node 而是包内 `bin/opencode.exe` —— 原 shim 解析只认 node 形态，报「Windows 仅支持原生 CLI 或标准 npm Node 启动器」。
   现在解析支持两种形态（node shim → 当前 Node 运行；exe shim → 直接运行该 exe），目标唯一且文件存在才放行。
2. **help 走 stderr**：`opencode run --help` 全文在 stderr，能力闸原判 stdout 读空 —— 改双流合并（与 Codex 登录状态解析同款先例）。
3. **登录表形态**：1.19.0 的 `auth ls` 输出是「Credentials / Environment 两段 + 计数行（带 `—` 装饰前缀）」，
   与 dev 分支的 stored/environment 列表不同 —— 解析改为计数行判定，读不懂升级为「检测未完成」而非误判未登录。
   修复后本机实测探针 ready（版本 1.19.0、OpenCode Go 凭据计数 1）。
